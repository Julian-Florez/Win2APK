Win2APK / manual operativo

Empaquetar una carpeta Windows para Android

Declara una carpeta ya preparada en un JSON, define su ejecutable, icono e identidad Android, y deja que el CLI genere e instale el paquete de prueba.

Alcance: aplicaciones y juegos distribuidos como una carpeta completa.

Ejemplo: Cuphead sirve para mostrar valores reales. No limita el procedimiento a ese juego.

Resultado: un AAB y, para pruebas locales, un APKS que ejecutan el programa de Windows mediante un entorno de compatibilidad. No es una conversión a código Android nativo.

Fecha: 2026-09-19. Describe el CLI Linux del esquema JSON v2.

01 / Entrada

Empieza con una carpeta Windows ya preparada

El CLI recibe el directorio final de la aplicación. No ejecuta instaladores ni intenta descubrir dependencias: allí deben estar el archivo .exe, sus bibliotecas, recursos y subcarpetas.

La carpeta adecuada

  • Contiene el ejecutable que debe abrirse.
  • Conserva la estructura relativa de todos los archivos.
  • Incluye dependencias privadas que la aplicación espera junto al ejecutable.
  • Proviene de una copia que puedes usar y distribuir legalmente.

Lo que no debes seleccionar

  • Un setup.exe que todavía debe instalar el programa.
  • Solo el ejecutable, si el programa utiliza archivos vecinos.
  • Una carpeta con DRM, anticheat o controladores de Windows que el entorno no soporte.
  • Datos cuyos permisos de distribución no tienes.
Compatibilidad no significa universalidad. El sistema empaqueta una carpeta y prepara Winlator para ejecutarla. Cada aplicación puede exigir otra versión de Wine, componentes de Windows, argumentos, controles o configuración gráfica. Empaquetar correctamente no garantiza que cualquier ejecutable funcione.

Requisitos del equipo Linux

  • Linux x86_64. Esta versión del host no admite Windows, macOS ni otras arquitecturas.
  • El repositorio Win2APK y su motor Android winlator/app.
  • Rust sólo para compilar el CLI desde el código fuente. El binario release instalado no requiere Rust.
  • Un dispositivo Android con ADB autorizado si se probará la instalación.
  • Espacio libre para el staging, el AAB, el APKS y la instalación en el dispositivo.

Instalar el binario release

Desde la raíz del repositorio, compila una vez y coloca el ejecutable en una ruta del PATH del usuario:

cargo build --release --package win2apk
install -Dm755 target/release/win2apk "$HOME/.local/bin/win2apk"

win2apk --version

Si $HOME/.local/bin no está en el PATH, añádelo al perfil de shell o invoca el binario mediante su ruta absoluta.

Preparar el toolchain y diagnosticarlo

win2apk setup
win2apk doctor --engine /ruta/al/Win2APK/winlator/app

setup descarga y verifica el JDK 17, Android SDK 36, NDK 30, CMake, platform-tools y bundletool. La aceptación de licencias de Android es interactiva. doctor comprueba el host, Java, SDK, ADB, bundletool y el motor antes de construir.

03 / Validación y plan

Deja que el CLI distribuya la carpeta

La carpeta original no se modifica. Win2APK la recorre, calcula tamaños y SHA-256, genera los asset packs on-demand y divide automáticamente los archivos que superen el tamaño objetivo.

  1. Valida antes de construir

    win2apk validate /ruta/al/proyecto.json

    Comprueba el esquema v2, Linux x86_64, las rutas, el icono, el applicationId y la existencia del entrypoint dentro de sourceFolder.

  2. Revisa la distribución calculada

    win2apk plan /ruta/al/proyecto.json
win2apk plan /ruta/al/proyecto.json \
  --output /ruta/al/plan.json

    El plan informa archivos, bytes, packs, segmentos y compatibilidad con los límites de Google Play. Este paso es de solo lectura.

  3. Distribución automática

    El CLI crea el staging, los módulos PAD, el manifiesto de payload y la configuración de runtime. No tienes que crear módulos de packs ni copiar archivos al motor Android.

    staging generado por Win2APK/
├── pack-01 ... pack-N/
├── icon-res/
├── payload-manifest.json
└── win2apk.json
La carpeta debe estar preparada. La automatización distribuye los archivos, pero no instala un setup.exe, no resuelve DRM o anticheat y no convierte dependencias de Windows en bibliotecas Android.

04 / Configuración

Define el nombre, la identidad, el icono y el runtime

El archivo JSON v2 es la única entrada del empaquetado. Las rutas relativas se resuelven desde el directorio que contiene el JSON.

Estructura mínima

Este ejemplo es genérico. Cuphead usa la misma estructura, pero con sus propios valores de carpeta, ejecutable, icono y configuración de runtime:

{
  "$schema": "../schemas/win2apk-v2.schema.json",
  "schemaVersion": 2,
  "project": {
    "name": "Mi Aplicacion",
    "sourceFolder": "/ruta/a/MiAplicacion",
    "entrypoint": "MiAplicacion.exe",
    "installDirectory": "MiAplicacion"
  },
  "android": {
    "applicationId": "com.ejemplo.miaplicacion",
    "versionCode": 1,
    "versionName": "1.0",
    "icon": "../assets/icons/mi-icono.svg",
    "iconBackgroundColor": "#1D5B45"
  },
  "packaging": {
    "delivery": "on-demand",
    "storageMode": "move",
    "targetPackBytes": 1350000000,
    "oversizedFiles": "chunk"
  },
  "distribution": {
    "aab": true,
    "apks": true,
    "localTesting": true
  },
  "signing": { "profile": "auto" },
  "startup": {
    "coreMode": true,
    "autoLaunch": true,
    "showGeneralInterface": false,
    "minimalLoading": true,
    "closeCoreWhenApplicationExits": true

  "container": {}
}

Icono local

Selecciona una imagen existente y coloca su ruta en android.icon. No se descarga desde Internet ni se guarda una copia en el repositorio automáticamente:

"icon": "../assets/icons/mi-icono.svg"

# o, si el icono está fuera del repositorio:
"icon": "/home/usuario/imagenes/mi-icono.png"

La ruta debe ser legible por el equipo de compilación. El CLI genera las variantes del launcher internamente.

No cambies el paquete ni la firma durante una actualización. Android considera otro applicationId como otra aplicación. Conserva el keystore original y aumenta versionCode. Nunca guardes contraseñas o claves privadas en el JSON ni en Git.

05 / Build

Construye AAB, APKS y reportes con una orden

El CLI orquesta el motor Android internamente. No debes entrar a winlator/app ni ejecutar Gradle manualmente.

win2apk build /ruta/al/proyecto.json \
  --engine /ruta/al/Win2APK/winlator/app

Si no se indica --output, la salida queda en dist/ junto al JSON. Puedes elegir otra carpeta y conservar staging para depuración:

win2apk build /ruta/al/proyecto.json \
  --output /ruta/a/salidas \
  --keep-staging

Qué automatiza build

  1. Valida la configuración y recorre sourceFolder sin modificarla.
  2. Calcula SHA-256, tamaño y ruta de cada archivo.
  3. Reparte los archivos en asset packs y segmenta los que superan targetPackBytes.
  4. Genera el icono, la configuración resuelta y el manifiesto que Android usará para mover el payload.
  5. Construye el AAB release, lo firma y genera el APKS mediante bundletool cuando están habilitados.

La firma automática se guarda fuera del repositorio en ${XDG_CONFIG_HOME:-$HOME/.config}/win2apk/keys/<applicationId>/. Para respaldarla antes de cambiar de equipo:

win2apk keys backup com.ejemplo.miaplicacion /ruta/segura/respaldo

06 / Instalación Android

Instala el APKS con el CLI

El AAB es el artefacto de distribución. Para probarlo localmente, build genera un APKS con localTesting y el CLI lo entrega a bundletool.

Comprobar ADB

adb devices -l

Autoriza el dispositivo y usa su serial si hay más de uno conectado.

Instalación nueva

win2apk install /ruta/al/dist/mi-aplicacion-1.0.apks \
  --device SERIAL \
  --fresh

--fresh desinstala explícitamente el paquete anterior y luego instala base, splits y asset packs. Elimina sus datos privados; úsalo sólo cuando se desea una prueba desde cero.

Actualización conservando datos

win2apk install /ruta/al/dist/mi-aplicacion-1.1.apks \
  --device SERIAL \
  --code-update

--code-update actualiza únicamente los APK del módulo base mediante ADB y conserva el payload y el contenedor instalados. Sin ninguna de las dos opciones, el CLI se niega a reemplazar una aplicación ya instalada.

Instalación no es lo mismo que primer arranque. Después de instalar, Winlator valida el payload, reconstruye archivos segmentados, mueve los archivos al prefijo y crea el shortcut. El tiempo hasta el primer frame depende del tamaño de la carpeta, almacenamiento y dispositivo.
ModoComportamientoDatos
Sin opciónRechaza reemplazar una instalación existente.Protegidos.
--freshDesinstala y ejecuta una instalación completa.Se eliminan.
--code-updateActualiza sólo el módulo base.Se conservan.

07 / Salida

Qué produce el CLI

La carpeta de salida es dist/ junto al JSON, salvo que se indique --output. El nombre de los artefactos combina el nombre del proyecto y versionName.

ArtefactoContenidoUso
<nombre>-<version>.aabApp Bundle firmado, con base, configuración y asset packs.Distribución o publicación compatible con App Bundles.
<nombre>-<version>.apksConjunto ZIP generado por bundletool para pruebas locales.Instalación mediante win2apk install o bundletool.
payload-manifest.jsonRutas, tamaños, SHA-256, packs y segmentos.Validación y reconstrucción del payload en Android.
resolved-config.jsonConfiguración runtime sin rutas de entrada del host.Configurar Winlator en el dispositivo.
build-report.jsonIdentidad, tamaños, hashes y compatibilidad Play.Procedencia del build; el CLI lo requiere para instalar.
checksums.sha256Hash de los artefactos AAB/APKS.Verificar integridad de la salida.
Un APK no siempre es un archivo único. Para carpetas grandes, el resultado local es un APKS compuesto por base, splits y asset packs. Android lo muestra como una sola aplicación, pero no debe instalarse sólo el APK base.

Después de instalar

El usuario toca el icono. La aplicación prepara el entorno de compatibilidad, valida el manifiesto, mueve el payload al prefijo de Wine y abre el entrypoint en project.installDirectory. El comportamiento de la interfaz y del contenedor se toma de startup, runtime y container.

08 / Limitaciones y diagnóstico

Qué puede fallar y qué no automatiza

La aplicación se instala, pero no aparece el juego o programa

Probablemente instalaste sólo el APK base o el APKS no contiene los packs. Usa el APKS producido por el mismo build, conserva junto a él build-report.json y vuelve a ejecutar win2apk install.

Android muestra INSTALL_FAILED_UPDATE_INCOMPATIBLE

La aplicación instalada y la nueva compilación tienen firmas distintas. Mantén el mismo applicationId y la clave persistente. Desinstalar permitiría instalar la nueva firma, pero elimina los datos privados; --fresh sólo debe usarse cuando eso sea intencional.

Aparece Unable to create the configured container or shortcut

Revisa project.installDirectory, project.entrypoint, el icono y el contenido de sourceFolder. Ejecuta validate y confirma que el ejecutable esté dentro del árbol preparado. El mensaje también puede indicar una incompatibilidad del contenedor o del runtime de Windows.

bundletool falla con un pack demasiado grande

El CLI divide automáticamente los archivos entre packs y segmenta los que superan targetPackBytes. Si el build excede los límites de Google Play, continuará para instalación local y lo marcará en build-report.json.

El icono anterior sigue visible

Confirma que android.icon exista y sea legible por Linux, aumenta versionCode y verifica que instalaste la nueva base con la misma firma. Algunos launchers conservan caché durante un tiempo.

El ejecutable abre, pero los gráficos fallan

Mantén graphicsDriver: "auto" y dxwrapper: "auto" en container para usar el perfil por dispositivo. Si la aplicación exige otra API gráfica, versión de DXVK o componentes de Windows, ajusta el JSON y registra una prueba separada. Un resultado en un modelo no demuestra compatibilidad con todos.

Android advierte que la aplicación fue creada para una versión anterior

La variante actual conserva targetSdkVersion=28 porque el entorno ejecuta Box64 y Wine desde el almacenamiento privado de la aplicación. Subir el target sin rediseñar esa ruta produjo un bloqueo SELinux en las pruebas del proyecto. La advertencia es una limitación conocida del prototipo para Android moderno.

El dispositivo no es compatible con el artefacto

La variante actual contiene únicamente arm64-v8a y requiere Android API 26 o posterior. El host de empaquetado debe ser Linux x86_64. El CLI no genera una aplicación Android nativa: ejecuta la carpeta Windows mediante Winlator, Wine y Box64.

El build de una carpeta muy grande tarda o consume mucho espacio

El staging, el AAB y el APKS pueden coexistir temporalmente. Cuphead produjo un paquete grande y necesitó cinco asset packs. Verifica el espacio libre antes de construir y ejecuta win2apk clean sólo para eliminar staging regenerable, nunca la carpeta fuente ni la clave.

Comandos básicos de diagnóstico

win2apk doctor --engine /ruta/al/Win2APK/winlator/app
adb -s SERIAL shell dumpsys package NOMBRE_DEL_PAQUETE
adb -s SERIAL shell pidof NOMBRE_DEL_PAQUETE
adb -s SERIAL logcat | rg 'Win2APK|AndroidRuntime|FATAL EXCEPTION'

El JSON completo está en config/win2apk.json. Para repetir el flujo, sustituye sourceFolder e icon por rutas de tu equipo y ejecuta:

win2apk setup
win2apk doctor --engine /ruta/al/Win2APK/winlator/app
win2apk validate config/win2apk.json
win2apk plan config/win2apk.json
win2apk build config/win2apk.json
win2apk install config/dist/cuphead-11.1-cuphead-core.apks \
  --device SERIAL \
  --fresh

Lista de control antes de construir otro paquete

  • La carpeta contiene el ejecutable final y todos sus recursos.
  • project.sourceFolder, project.entrypoint y project.installDirectory describen la misma aplicación.
  • android.applicationId es válido y permanecerá estable.
  • El icono existe y tienes permiso para usarlo.
  • packaging usa on-demand, move y chunk.
  • win2apk validate y win2apk plan terminan correctamente.
  • El versionCode es mayor que el de la versión que vas a actualizar.
  • La compilación reutiliza la misma clave persistente de las versiones anteriores.
  • La prueba se hará primero en un dispositivo y conservará logs antes de ampliar la conclusión.
